# TaskRadar

## Проблема

Я веду одновременно несколько направлений работы плюс сам исполняю часть задач, плюс параллельно двигаю несколько проектов, которые пишут AI-агенты. Рабочая модель сейчас — окно VS Code на проект, сессия агента на поток внутри проекта. Это работает, пока активных проектов 2-3: они физически открыты, между ними легко переключаться.

Как только проектов становится больше, лишние уходят в фон. Проблема не в том, что задачи негде записать — проблема в том, что **восстановление контекста по забытому проекту стоит дорого**: нужно заново поднимать VS Code, вспоминать, на чём остановился и что делать дальше. Плюс часть задач вообще не идёт через агентов — их делают другие люди или я руками — и для них сейчас нет общего места рядом с остальным.

TaskRadar — не трекер задач в классическом смысле, а инструмент **восстановления контекста**: попадая в любой проект, даже забытый на две недели, за секунды понятно, что происходило и что дальше.

## Что это

Список из 10-15 личных проектов, каждый — колонка на доске. Заходишь утром, смотришь на всё разом, выбираешь, чем заниматься, в течение дня отмечаешь прогресс, периодически возвращаешься проверить фон.

## Модель данных (MVP)

- **Project** — архивируется (обратимо) или удаляется (необратимо). Внутри — несколько markdown-заметок (идеи, контекст, что угодно текстом).
- **Task** — плоский упорядоченный список внутри проекта. Статусы: `pending` / `done` / `blocked`. Текущая задача — первая не done и не blocked по порядку, вычисляется автоматически.
- **Blocked + напоминание** — у задачи можно поставить `blocked` вместе с датой напоминания («жду кабель, спросить завтра»). Идеологически это принадлежит уровню потока работ, но пока потоков как сущности нет — живёт на задаче.

Никаких потоков/направлений как отдельной сущности, никакого отдельного среза "на сегодня" вне досок, никаких меток исполнителя — если это важно, это просто текст в описании задачи.

## Осознанно не делаем (и почему)

| Что | Почему |
|---|---|
| Гантт / таймлайн | Ось — календарное время, а нужная ось — порядок выполнения |
| Ассайны, спринты, роли, мульти-пользователь | Инструмент для одного человека, не команды |
| Зависимости между задачами | Нет сложных взаимосвязанных задач — не тот случай |
| Потоки/направления как сущность | Отложено: усложняет модель, а реальная боль (восстановление контекста) закрывается и плоским списком |
| Оффлайн-редактирование с синхронизацией | Самая тяжёлая техническая часть, ценность для v1 не окупает риск не доехать до готового инструмента |
| Отдельный "сегодня"-срез, вложения, поиск | Доски и так помещаются на экран целиком при 10-15 проектах |

## Почему не готовый инструмент

Trello / Planka / Vikunja и любой другой канбан ломаются об одну и ту же вещь: в схеме "колонка = проект" проект превращается в список, а у списка нет тела — ни описания, ни заметок, ни вложений. Класть контекст проекта некуда. Командные тулы (Plane, OpenProject, Redmine, Taiga) построены вокруг ассайнов и спринтов, которых тут нет. Гантт/таймлайн-инструменты (Markwhen и подобные) используют не ту ось. Прямое требование к модели данных, отсюда: **проект — сущность первого класса с телом, а не контейнер**.

## Стек

- **Клиент: Flutter (Dart), одна кодовая база на два таргета — Android и Windows.** На десктопе это обычное приложение, на телефоне — обычное приложение с нативными уведомлениями
- Бэкенд: Node.js + TypeScript + Fastify, REST API
- БД: PostgreSQL + Prisma
- Auth: один пользователь, пароль + JWT; нативный клиент носит токен в заголовке `Authorization` и хранит его в защищённом хранилище ОС
- Деплой: один VPS, Docker Compose, Caddy как reverse-proxy

Работает только онлайн. Локально кэшируется **на чтение** последний снимок доски — чтобы экран открывался мгновенно и чтобы телефон знал даты напоминаний без сети. Любая запись требует сети: очереди операций и разрешения конфликтов нет, оффлайн-редактирование по-прежнему сознательно отложено.

### Почему клиент нативный, а не веб

Первая версия клиента была React + Vite PWA. На реальном телефоне выяснилось, что веб-страница не может быть надёжным источником напоминаний: Web Push на Android душится энергосбережением. А напоминание по `remindAt` у заблокированной задачи — не украшение, а единственная причина, по которой в инструмент возвращаешься («жду кабель, спросить завтра»). Если оно не приходит — инструмент не выполняет свою работу.

Второй мотив — голосовой ввод локальной ASR-моделью (ближайшая фича после MVP): в браузере он невозможен в нужном виде, нужна модель в памяти процесса и свой кэш на диске.

Уведомления в нативном клиенте — **локальные будильники, а не push**: сервер ничего не шлёт, приложение само планирует их по датам из `remindAt`. Гранулярность напоминаний дневная, поэтому синхронизации в фоне достаточно.

Итерации 0-6 (модель данных, API, авторизация, доска, экран проекта, напоминания/архив) реализованы на бэкенде и в старом React-клиенте. Клиент переводится на Flutter, бэкенд остаётся без изменений кроме нескольких аддитивных эндпоинтов.
