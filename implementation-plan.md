## Итерация 0 — Скелет проекта

**Цель:** поднять пустой каркас, на котором дальше пишется всё остальное, без единой строчки продуктовой логики.

**Что делаем:**
- Монорепозиторий: `/backend`, `/frontend`, `/docker`
- Backend: Node.js + TypeScript + Fastify, один health-check роут (`GET /health`)
- Prisma подключена к PostgreSQL, схема пустая (одна тестовая таблица или вообще без моделей)
- `docker-compose.yml` для локальной разработки: postgres + backend с hot-reload
- Базовый линтер/форматтер (eslint + prettier) на backend

**Результат:** `docker compose up` из чистого клона репозитория поднимает Postgres и backend, `curl localhost:PORT/health` отвечает 200.

## Итерация 1 — Модель данных и API

**Цель:** вся структура данных из README реализована и доступна по HTTP, ещё без авторизации и без интерфейса.

**Что делаем:**
- Prisma-схема: `Project` (name, archived_at, deleted_at, timestamps), `Task` (project_id, title, description, status: pending/done/blocked, position, remind_at), `Note` (project_id, title, content markdown, timestamps)
- Миграции применяются через `prisma migrate`
- REST-эндпоинты:
  - Project: создать, список (без архивных по умолчанию), получить один, архивировать, разархивировать, удалить (только если уже архивирован)
  - Task: создать в проекте, список по проекту (в порядке `position`), обновить (título/описание/статус/`remind_at`), переставить порядок, удалить
  - Note: создать в проекте, список по проекту, обновить, удалить
- Простая валидация входных данных (например, через Zod)

**Результат:** через curl/Postman можно полностью прожить сценарий — создать проект, добавить туда 3 задачи, поменять их местами, пометить одну как blocked с датой, добавить заметку, заархивировать проект — и всё это переживает перезапуск сервера (данные в Postgres).

## Итерация 2 — Авторизация

**Цель:** закрыть API от посторонних, учитывая, что пользователь один.

**Что делаем:**
- Единственный пользователь задаётся через переменные окружения (логин + bcrypt-хэш пароля, либо хэш генерируется скриптом при первом старте)
- Эндпоинт логина: проверяет пароль, выдаёт JWT в httpOnly-cookie
- Middleware на все Project/Task/Note роуты, требующий валидный токен
- Эндпоинт логаута (чистит cookie)

**Результат:** без логина все API-запросы из итерации 1 возвращают 401; после логина с верным паролем те же запросы работают как раньше.

---

## Итерация 3 — Доска (список проектов)

**Цель:** первый раз увидеть продукт в браузере — доску, о которой был весь исходный разговор.

**Что делаем:**
- Frontend: React + TypeScript + Vite, минимальный роутинг (страница логина, страница доски)
- Страница логина, вызывающая API из итерации 2
- Доска: колонка на проект, в колонке — вертикальная линия задач, цвет по статусу (pending/done/blocked), текущая задача (первая не done/blocked) визуально выделена
- Загрузка данных с backend, без кэширования и офлайна

**Результат:** залогинившись в браузере на десктопе, видно реальную доску с реальными проектами и задачами, заведёнными в итерации 1 — визуально похоже на исходный макет "колонка = проект, линия сверху вниз".

## Итерация 4 — Проект изнутри

**Цель:** провалиться в проект и полноценно с ним работать, не трогая API напрямую.

**Что делаем:**
- Экран проекта: список задач (создать, редактировать текст, поменять статус, перетащить для смены порядка, удалить)
- Заметки проекта: список markdown-документов, создание/редактирование/удаление, простой markdown-рендер при просмотре
- Переход с доски в проект и обратно

**Результат:** весь дневной цикл ведения одного проекта (завести задачи, двигать их, писать заметки) делается мышкой в браузере, без единого прямого запроса к API.

## Итерация 5 — Блокер с напоминанием, архив и удаление в UI

**Цель:** закрыть оставшиеся кусочки продуктовой логики, чтобы инструментом можно было пользоваться каждый день вместо текущего способа.

**Что делаем:**
- UI для установки `blocked` + даты напоминания на задаче; на доске и в проекте задачи с наступившей датой напоминания визуально выделяются (например, другой оттенок/пометка "проверить")
- Архивация проекта из UI (уходит с доски, но доступен в отдельном списке архива) и удаление (только для уже архивированных, с подтверждением — необратимо)
- Полировка доски: если проектов много, всё ещё помещается на экран без прокрутки в две стороны

**Результат:** можно провести полный рабочий день внутри TaskRadar — от утреннего обзора доски до пометки заблокированных задач с напоминанием на завтра — без обращения к старому способу учёта.

## Итерация 6 — Адаптивность и PWA

**Цель:** тот же функционал удобно работает с телефона.

**Что делаем:**
- Адаптивная вёрстка доски и экрана проекта под узкий экран
- PWA-манифест + service worker, кэширующий только статику (не данные) — возможность "добавить на домашний экран"
- Ручная проверка на реальном телефоне: доска, открытие проекта, отметка задачи

**Результат:** TaskRadar открывается с телефона как отдельная иконка на домашнем экране, интерфейс не требует масштабирования и горизонтальной прокрутки.

## Итерация 7 — Скоупы проектов

**Цель:** разделить проекты по нескольким независимым пространствам (например: работа — компания A, работа — компания B, личное, дом, дача) и переключаться между ними на доске, не смешивая всё в одном списке из 10-15 колонок.

Это не то же самое, что «потоки/направления внутри проекта», отложенные в README и в `project-tracker-brief.md` — потоки группировали бы задачи *внутри одного* проекта, а скоуп группирует *сами проекты* по тому, к какой сфере жизни они относятся. Модель задач и заметок внутри проекта не меняется.

**Что делаем:**
- Prisma-схема: сущность `Scope` (id, name, position, timestamps); `Project` получает обязательное поле `scope_id`. Одна миграция создаёт дефолтный скоуп и переносит в него все существующие проекты, чтобы ничего не потерялось.
- REST-эндпоинты: создать скоуп, список скоупов, переименовать, изменить порядок, удалить (только если в нём не осталось проектов — либо с обязательным переносом проектов в другой скоуп при удалении).
- Создание/редактирование проекта — выбор скоупа.
- UI: переключатель скоупов над доской (вкладки или выпадающий список), доска показывает проекты только выбранного скоупа; выбор запоминается между визитами (например, в localStorage).
- Архив (итерация 5) тоже фильтруется по текущему скоупу.

**Результат:** можно завести отдельные скоупы под разные сферы (работа в одной компании, работа в другой, личные дела, дача) и мгновенно переключаться между ними — доска в каждый момент показывает только один скоуп, а не все 10-15+ проектов сразу.

## Итерация 8 — Деплой на VPS

**Цель:** TaskRadar живёт не на локальной машине, а на постоянном адресе, доступном с любого устройства.

**Что делаем:**
- `Dockerfile` для backend и для сборки frontend
- `docker-compose.prod.yml`: postgres + backend + Caddy (reverse proxy, автоматический TLS по домену)
- Настройка VPS, перенос переменных окружения/секретов, первый деплой
- Резервное копирование БД (простой периодический дамп)

**Результат:** TaskRadar открывается по HTTPS-домену с телефона и с Windows-компьютера, данные переживают перезапуск сервера, есть бэкап на случай сбоя.

## Отклонение от плана: локальный Postgres вместо Neon

Изначально для dev/prod брали облачный Neon (бессерверный Postgres), чтобы не трогать Docker/WSL2 на этой машине. На практике сеть этой машины стабильно рвёт соединение к Neon примерно на 20-й секунде (`P1017`/`ConnectionReset`) — воспроизводится и в CLI (`prisma migrate`), и в `@prisma/client` при нескольких запросах подряд. Диагностика показала: сама база и обычный TCP/TLS не виноваты (`pg`-драйвер и одиночные запросы через `@prisma/client` проходят быстро), проблема воспроизводима именно на этой сети при повторных подключениях — похоже на особенность локальной сети/антивируса, а не Neon.

Решение: PostgreSQL 17 поставлен нативно через winget (`PostgreSQL.PostgreSQL.17`), без Docker и без WSL2 — обычный Windows-сервис на `localhost:5432`, база `taskradar`. Это быстрее и надёжнее для итераций 0-6. Вопрос прод-БД (снова Neon, VPS-Postgres или что-то ещё) — решать в итерации 8, когда дойдём до реального деплоя.
