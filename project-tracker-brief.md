# TaskRadar — обоснование модели данных и отсечённые альтернативы

## Исходная задача

Простое ведение личных проектов: нет сложных взаимосвязанных задач, нет множества исполнителей. Наглядность — последовательные этапы проекта в виде линии сверху вниз, статусы обозначены цветом, отдельным цветом — задача-блокер. Нужно за секунды посмотреть на 10-15 проектов разом, понять текущее состояние каждого, выбрать один и продолжить работу.

После первого макета «колонка = проект» добавились ещё два требования: провалиться внутрь проекта и вести там заметки/идеи текстом; часть проектов не показывать на общей доске, а переносить в архив.

## Решение

Разработка собственного инструмента вместо использования готовых.

## Требования к хранению и доступу

- Данные хранятся на сервере, не только локально.
- Доступ с телефона и с десктопа.
- Текущий этап проекта вычисляется автоматически (первая незавершённая и незаблокированная задача по порядку).
- Инструмент — основной способ ничего не забыть, а не вспомогательный.

## Отсечённые классы решений

| Класс | Почему не подходит |
|---|---|
| Гантт и таймлайны | Ось — календарное время, а нужная ось — порядок выполнения. Даты пришлось бы поддерживать без отдачи |
| Командные тулы (Plane, OpenProject, Redmine, Taiga) | Построены вокруг ассайнов, спринтов и зависимостей, которых здесь нет |
| Markwhen и подобные markdown-таймлайны | Тоже ось времени, плохой быстрый ввод |

## Рассмотренные и отвергнутые готовые инструменты

Trello, Planka, Vikunja, Obsidian + Bases, самодельный рендер статической страницы из markdown.

### Ключевая причина, почему готовые канбаны не подошли

В схеме «колонка = проект» проект оказывается **списком**, а у списка нет тела — ни описания, ни вложений, ни заметок. Класть контекст проекта некуда. Это ломает Trello, Planka и Vikunja одинаково.

Отсюда прямое требование к модели данных: **проект — сущность первого класса с телом, а не контейнер.**

### Прочие наблюдения по ходу

- В `kanban-bases-view` (Obsidian) цвет привязан к колонке, а не к карточке — четыре состояния этапа пришлось бы тянуть через теги и CSS.
- В Trello архив списка обратим, а удаление возможно только после архивации и необратимо. Разделение обратимого архива и необратимого удаления стоит скопировать.
- Обходные костыли, рассмотренные до решения писать своё: мета-карточка «— контекст —» первой в списке; `archived: true` во frontmatter + фильтр.
- Не проверено на практике: предположение, что в Vikunja архив попадает не на тот уровень модели (архивируются проекты, а в перевёрнутой схеме проекты — это bucket'ы) — вывод сделан из документации модели данных, в UI не проверялся.

## Пересмотр модели (потоки внутри проекта)

Первый проход через открытые вопросы (оффлайн-режим, группировка задач, стек, хостинг) дал модель `Project → Threads (потоки/направления внутри проекта) → Task`. При дальнейшем анализе цели это оказалось переусложнением для первой версии.

Уточнённая проблема: не нехватка канбана, а **дорогое восстановление контекста** по проекту, ушедшему в фон. Рабочая модель "окно IDE = проект, сессия агента = поток" держится только при 2-3 активных проектах; при большем числе лишние проекты забываются и их приходится поднимать заново. Плюс задачи, которые делают не агенты, а руками или другие люди, сейчас негде вести рядом с остальным.

Решения по итогам пересмотра:

- **Потоки убраны из модели v1.** `Project` → плоский упорядоченный список `Task`. Если понадобится группировка задач одного проекта — решать лёгкой меткой на задаче, не отдельной сущностью.
- **Блокер + напоминание по дате** — задача может иметь `blocked` + `remind_at`. Идеологически это атрибут уровня потока (пример: «жду внешнюю зависимость — весь этот участок работы стоит»), но раз потоков нет — временно живёт на `Task`.
- **Отдельный срез "на сегодня" вне досок — не нужен.** Досок проектов достаточно для планирования.
- **Пометка "кто делает / от кого ждём" — не нужна.** Обычная задача без спец. поля, при необходимости — текст в описании.
- **Название: TaskRadar.**

## Что подтвердилось без изменений

Архивация (обратимая) / удаление (необратимое) проекта, несколько markdown-заметок на проект (документы в БД, не файлы на диске), онлайн-only для v1, один пользователь, стек Node.js/TS + Fastify + PostgreSQL/Prisma + React/Vite PWA, деплой на VPS через Docker Compose.

Актуальное описание модели и обоснование — в `README.md`.
